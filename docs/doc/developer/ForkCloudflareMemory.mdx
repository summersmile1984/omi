---
title: 'Cloudflare memory writes'
description: 'Canonical write admission and durable projection work in the fork Cloudflare target'
---

The isolated Cloudflare target owns memory rows in App D1 `cf_memories`.
New native, MCP and Developer memory intake starts in Short-term, including
manual memories and batches. `category`, `manually_added` and `durability` do
not grant Long-term admission. Existing Long-term records retain their tier
until an explicit content correction or another canonical lifecycle action.
The shared Server/Cloudflare HTTP contract verifies creation, persisted tier,
editing and deletion; full canonical consolidation remains a separate
implementation and qualification requirement.

With migration 0172, native `POST /v3/memories` and
`POST /v3/memories/batch` persist memory content, evidence, operation receipts,
commit records and pending index work atomically with usage and review work.
The batch request remains `{"memories": [...]}`, with at most 100 memories
and a **1,000,000-byte UTF-8 request body**, including the JSON envelope and
metadata. The single-memory content limit remains 50,000 characters. Larger
requests return HTTP 413 with `error: "memory_batch_too_large"`, `max_bytes`
and `max_memories`, without writing any items. Clients must split imports by
both encoded size and item count; each request is a separate transaction.
The macOS fork importer does this automatically for the Cloudflare target,
while retaining per-batch success/failure counts and account-switch protection.
A failed transaction returns 503 without a partial
batch. Repeating a public POST allocates new IDs; this API does not accept a
client-authored operation or ledger head.

Cloudflare operators must provision one stable `MEMORY_PRIVACY_SECRET` of at
least 32 UTF-8 bytes to API Core and Jobs. Keep it separate from authentication
credentials and retain it across releases. Migration 0174 and the current
creators use this key for internal deletion-receipt identities. These values
are absent from API memory objects and exports; clients do not provide them.
Replacing the secret requires a coordinated rekey migration.

Migration 0175 adds canonical deletion preparation: complete-lineage selection,
transaction-time account/head/item checks, content scrubbing, a new privacy
commit and sealed deletion receipts. A content-free cleanup inventory survives
provider failures. Migration 0176 connects native single/batch/all/default,
MCP and Developer deletion to this owner and guards final physical erasure.
The new legal-hold/destructive gate authority is server-owned; no user request
may create a hold or choose an operation token. It protects canonical memory
deletion, rather than all Cloudflare deletion families.

Deletion returns HTTP 200 only after vector cleanup and physical memory/history
erasure. While an external writer or provider deletion is pending, it returns
503 with `error: "memory_cleanup_pending"` and `Retry-After: 2`. The existing
Jobs Queue and schedule continue the durable request without another client
call. Jobs uses signed private Core continuations; Core rechecks authority and
artifact/mapping absence inside the final D1 transaction. A provider accepting
an asynchronous deletion is insufficient to acknowledge success.

All/default deletion persists its scope across batches of at most 100 items.
Default retains Archive, including linked Archive records. Finalization removes
referencing journal, review, Archive and lifecycle history as well as the memory
row. Source conversations and imported source artifacts remain. Removing memory
usage-source identities also removes their contribution to historical usage
counts. Opaque 30-day receipts allow idempotent retries after finalization;
pending cleanup continues to fence late writers even if a receipt expires.
Unknown IDs return 404. Developer deletion retains its active paid-lock check
(402); native privacy deletion remains available for locked memories.

The local actual Workers recording flow verifies indexed memory deletion and
autonomous Jobs completion with a controlled Vectorize provider. See the
[deletion verification record](../../../dev/unified-main/implementation-2026-09-05/memory-privacy-delete-2026-09-07.md)
for the exact verification scope and remaining production requirements.

Migration 0173 moves native `PATCH /v3/memories/{id}` content corrections into
the same transaction as the operation receipt, commit/head and pending index
work. Corrected content returns to pending Short-term and clears the previous
graph admission, following the upstream correction policy. Old vector mappings
are revoked while the revised content awaits processing. Pre-journal memories
are adopted in place when edited; their IDs and capture provenance are retained.
Closed or superseded records cannot be reopened by this endpoint. Locks return
402; concurrent target/head/generation changes and failed writes return 503
without a partial correction.

Native visibility, review votes, read/dismiss and baseline changes also use the
canonical mutation transaction. They retain their existing request and response
shapes, paid-lock admission and owner isolation. A concurrent target/head change
returns 503 without a partial item, journal or feedback update. Product metadata
changes preserve content and tier; a positive vote does not promote a pending
memory. Review rejection/reacceptance follows the original processing-status
policy. Belief processing remains at the target's default-off setting.

Migration 0177 persists an existing graph-backed Long-term memory's refreshed
graph assertion in that same transaction. The exact current item revision and
admitted target guard must authorize the assertion. It is included in owner
export and removed by memory privacy/account erasure. This completes graph
storage for these user mutations and the consolidation adapter below. Shared
graph-query convergence is still unfinished. See the
[product-mutation verification record](../../../dev/unified-main/implementation-2026-09-05/memory-product-mutation-2026-09-07.md).

Review-queue resolution also shares canonical apply and privacy deletion.
Acceptance and correction return the candidate to pending Short-term; they do
not invalidate conflict peers or grant promotion. A correction's target ID is
audit metadata for this canonical route. Rejection and low-confidence timeout
remove the candidate's canonical lineage and derived history. While provider
cleanup remains pending, resolution returns 503 `memory_cleanup_pending` with
`Retry-After: 2`; a retry resumes cleanup before acknowledging completion.

Review source identity is its actual commit, item revision, content hash and
consolidation `review` route. Historical timestamp-based rows become stale and
cannot write. Native intake no longer derives review decisions from conflicting
fields; the consolidation persistence adapter now creates reviews from validated
model decisions, while its scheduled model producer remains unfinished. Completed
privacy erasure removes its review projection, so subsequent retrieval returns
404. Accepted/corrected decisions remain redacted and replay without a new
commit. [Verification record](../../../dev/unified-main/implementation-2026-09-05/memory-review-canonical-2026-09-07.md).

`memory_consolidation_apply.apply_consolidation_batch` persists up to 20 upstream
decisions in one D1 transaction. It validates the complete partition and reloads
all model-referenced sources before admitting any writes. Required normalization,
promotion admission receipts, graph assertions, supersession, Archive/review/reject
outcomes and journal/outbox records share that transaction. A concurrent account,
source or candidate change requires fresh planning; storage failure rolls back
the whole batch. Review records use the original deterministic source-bound
builder and are consumable by the existing public review API.

The adapter does not yet enable scheduled consolidation. Candidate retrieval,
real model invocation, leases/retries and recurrence handoff remain unfinished;
recurrence-bearing batches are rejected before writes until their workflow owner
is connected. Native intake normalization and default-read alignment also remain
required. No default prompt was changed. See the
[consolidation verification record](../../../dev/unified-main/implementation-2026-09-05/memory-consolidation-apply-2026-09-07.md).

The user export includes owned operations, commits and graph assertions under
`memory_ledger_data`. These native intake and user-mutation records do not
yet constitute complete history for other writers,
source deletion or consolidation. History/revert and JIT
remain unqualified until every writer shares the same authority.

Migration 0161 enforces the current row's paid-plan lock inside interactive
updates. A lock acquired after an API pre-read still returns 402 and rolls back
the transaction. Database failures return 503. Privacy tombstones and account
erasure remain available for locked rows.

Migration 0162 commits each mutation's monotonic `item_revision` and vector
projection outbox together. Wall-clock `updated_at` remains a presentation
timestamp; two edits in the same second receive distinct revisions. Existing
rows are rebased above prior stored and pending timestamp versions. Creation
also advances beyond a pending deletion when an identity is recreated. Records
behind an account-deletion fence are left to that erasure owner.

Native memory routes, MCP, developer API, X extraction and conversation cascade
deletion share this database authority. A failure to persist projection work
rolls back the memory mutation; a downstream model or Vectorize failure leaves
durable retry work after the business write has committed. Existing notification
calls wake Jobs after commit; scheduled reconciliation also drains the outbox.

The `cf_memory_projection_sources` view centralizes index eligibility: active,
processed source, current account generation, no expired capture, paid-plan lock,
archive tier, rejection or restricted sensitivity label. A missing user review
is distinct from explicit rejection. Jobs uses the source revision when reading
and acknowledging work. An edit while embedding is in flight leaves its later
revision queued for another pass.

Migration 0163 assigns each external memory-vector publication a unique attempt
and immutable vector IDs. D1 records these IDs before calling Vectorize. The
publication transaction compares the current source content and revision;
an older task cannot overwrite the current mapping or vector bytes. Canonical
revision changes revoke old serving mappings in the same transaction. Deletion
work only retracts mappings through the revision it observed.

The artifact journal survives lost provider responses and account deletion.
A successful write receipt releases its writer; an uncertain write retains the
full 15-minute Queue/cron invocation bound. Cleanup retires unreferenced IDs and
waits for observed absence after a previously observed vector, or an exact
processed deletion receipt. It does not infer completion from local timestamps
or from acceptance of an asynchronous mutation. Account erasure remains pending
until the journal is empty. Hosted cleanup latency still requires qualification.

Individual memory projection deletion tasks also retain their exact outbox
record until the artifact owner confirms cleanup. Queue delivery retries while
an eligible writer or external deletion is pending. The check covers only the
owner, memory and revisions through the task's observed revision; unrelated
memories and newer publications remain independent. This acknowledges the
projection task, not complete canonical privacy deletion: the public deletion
transaction and history finalization still require migration to the shared
canonical apply owner.

Full-migration ASGI/SQLite regressions cover admission races, same-second edits,
transaction rollback, upgrade state and cascade deletion. The existing product
lane runs real local Auth, Workers, D1, Queue and R2 through public HTTP/WebSocket
recording, memory mutation, export, cascade deletion and account erasure.
Its inference IO remains controlled, and that product lane does not exercise
hosted Vectorize. The Worker suite separately drives the production projector
through real SQLite transactions and controlled asynchronous Vectorize IO.

Native, MCP, developer and chat-tool vector searches now use one canonical D1
snapshot for memory content, revision, model/publication metadata and access.
The result limit is applied after rejection and chunk deduplication. Native
diagnostics distinguish missing items, stale projections, stale vector IDs and
access denials; the hydration read count includes rejected candidates.

Repairs recheck canonical intent in the write transaction, preserve a newer
publication, and reuse the existing artifact journal and projection outbox.
Due work receives a post-commit Queue hint. The native
`repair_purge_outbox_records` contains actual pending D1 artifact records,
identified by vector ID and `storage: cf_memory_vector_artifacts`; these are
not fabricated Firestore records. Unknown provider IDs without a trusted
uid-scoped owner are counted and logged without authorizing external deletion.

Equivalent publication ownership for the other projection families remains
required, along with hosted provider qualification. Ledger
history/revert also require append-only lineage and exact idempotency. These
remain tracked in the fork CF-4 migration ledger and block full production
product qualification; no default prompts or extraction policies are changed.
