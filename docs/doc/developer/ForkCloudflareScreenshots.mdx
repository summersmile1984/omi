---
title: "Cloudflare meeting screenshots"
description: "Screenshot display, settings and revocation for clients using the Cloudflare target"
---

The screenshot API is under development in the Cloudflare target. Core implements
candidate adjudication, display and revocation; the public Edge route family remains
unavailable until hosted model access and the complete workflow are qualified.
Do not use these implementation results as evidence of a live deployment.

An authenticated `GET /v1/screen-frame-egress/settings` returns
`meeting_note_screenshots_enabled`, which defaults to true for existing accounts
without a settings record. PATCH the same route with that boolean to change it.
Disabling screenshots hides retained images on owner and shared views and makes
existing image URLs unavailable. Enabling it restores retained images.

`GET /v1/conversations/{conversation_id}/screenshots` returns the owner's frame
set: `revision`, nullable `banner`, up to six `strip` frames and nullable
`adjudicated_at`. Use `adjudicated_at` to determine whether candidate evaluation
already ran; a zero revision alone does not mean it has never run.

Each frame includes `content_url`, `thumbnail_url`, `url_expires_at`, caption,
labels, dimensions and server-derived background colors. Image URLs last at most
one hour and are rechecked against current privacy state on every read. Treat
them as opaque capabilities and obtain fresh URLs by reloading the frame set.
Responses are not cacheable.

PATCH `/v1/conversations/{conversation_id}/screenshot-sharing` with
`{"enabled": false}` to withdraw screenshot sharing. This leaves the conversation's
other sharing state and the screenshot revision unchanged. Shared screenshot URLs
then become unavailable; owner URLs remain usable when screenshots are enabled.

The unauthenticated
`GET /v1/conversations/{conversation_id}/shared/screenshots` returns an empty set
when the conversation is missing, private, no longer shared or screenshots are
disabled. Those cases all return 200. Public lookup uses the existing unique
conversation share owner.

DELETE `/v1/conversations/{conversation_id}/screenshots/{frame_id}` removes one
frame and may promote another already-approved survivor to banner. Deleting a
missing frame returns 404. DELETE `/v1/conversations/{conversation_id}/screenshots`
removes the whole set, including when it is already empty. Both return the
updated set and increment its revision. Removed image URLs become unavailable
immediately after the committed mutation; physical object cleanup is retried by
the storage service. Deletion preserves `adjudicated_at`.

Candidate submission uses `POST /v1/screen-frame-egress/adjudications` with
`schema_version: 1`, a UUID `attempt_id`, `purpose: "meeting_note_v1"`,
`subject: {"kind": "conversation", "id": "conversation-id"}` and one to eight
`candidates`. Each candidate provides `client_frame_id`, `captured_at`,
`mime_type`, `declared_width`, `declared_height`, `sha256_base64` and `bytes_base64`.
The conversation must be owned and completed; captures must fall within its
time window with the existing two-minute slack.

Every transport digest is checked before model processing. Core standardizes
the image and judges those exact bytes with the upstream privacy prompt and
strict output schema. A client verdict cannot approve an image. Rejected or
unreadable candidates are omitted; a failed approved-image write returns 503.
The successful result contains `attempt_id`, `outcome` (`committed` or
`no_approved_frames`) and `frame_set`.

Repeating an attempt with the same request replays its stored response for
24 hours; a different fingerprint returns 409 and an unfinished attempt returns 503. An all-rejected pass updates `adjudicated_at` while leaving revision
unchanged. At most seven approved frames survive, with up to one banner and six
visible strip entries. Turning screenshots off or deleting the subject during
processing prevents pending images from being published.
