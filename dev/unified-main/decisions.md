## 第 1 组 · 阻塞 S1（下一步），建议本周签

### D1 · 部署 profile 的两个轴

**问题**：客户端与后端用什么维度描述"部署在哪"？

**选项**

| 方案 | 后果 |
|---|---|
| **A（推荐）两轴分离**：`deployment_target ∈ {omi_cloud, self_hosted, cloudflare}` × `stage ∈ {production, beta, local}`，身份提供方由 target 派生 | 语义干净；`self_hosted.local` 与 `self_hosted.production` 天然区分；加第四个 target 不动 stage |
| B 单轴枚举（沿用上游 `production/mobile_beta/local_prod/local_dev` 再往里塞 `self_hosted`、`cloudflare`） | 就是两条分支现在各自的做法；枚举会组合爆炸（3 目标 × 3 环境 = 9 个值），且"自托管的 beta"无法表达 |

**推荐 A。** 两条分支已经各自证明了 B 的问题：shim 分支把 `selfHosted` 塞进环境枚举后，`self_hosted` 到底是哪个 stage 说不清；CF 分支干脆不表达 stage。

**阻塞**：S1（profile 单一事实源与生成器）、S2/S3/S4/S5 全部读这张表。
**改主意的代价**：**低**（S1 之后、S2 之前改，只动生成器；S2 之后改要重跑四端接线）。

### D2 · 契约权威：谁定义客户端看到的 API

**问题**：自托管和 Cloudflare 两个后端，客户端契约以谁为准？

**选项**

| 方案 | 后果 |
|---|---|
| **A（推荐）上游 API 是契约，自托管是参考实现，Cloudflare 单向对齐** | 客户端只有一份实现；上游每次改 API，两个后端一起跟；Cloudflare 的内部机制（Worker 间断言头、DO、D1）不进契约 |
| B 各目标各自演进契约 | 客户端要按 target 分叉；`auth_service.dart`、`api.ts` 变成两份；上游同步时两份都要重套 |

**推荐 A。** 具体含义（这些是 CF 分支现有实现要**回退**的部分）：

- 认证路径统一 `/api/auth`（CF 现在是 `/api/better-auth`）
- 服务端用 **JWKS 本地校验**（CF 现在每请求调 `/internal/verify`；它已声明 `BETTER_AUTH_JWKS_URL` 却未使用）
- JWT TTL 可配，默认 3600s（CF 现在写死 24h，移动端还自造过期时间）
- 移动端走**真实 Better Auth 流程**（CF 现在只有 `!kReleaseMode` 的开发桥，无刷新）
- 实时沿用上游 `/v4/web/listen` **首帧 token**（CF 引入的 web-ticket 与 bootstrap 头不保留）
- 不新增上游没有的端点（CF 的 `/v1/capabilities`、409 账户围栏降为内部实现）

**阻塞**：S2、S4、S5、S6、M2。
**改主意的代价**：**中**（M2 之前改只动 CF 目录；M2 之后改要重做 Worker 与客户端两侧）。

**值得你确认的一点**：Cloudflare 那条线已有一套跑起来的独立生产（`workers.dev` 域，无真实用户）。按 A 对齐会让它的 D1 数据面重建一次。我认为这个代价现在付最便宜——它没有真实用户，且越晚越贵。

### D5 · 向量维度

**问题**：两个目标的 embedding 维度不同，怎么处理？

**事实**：Cloudflare Vectorize 上限 1536 维；上游截图/记忆路径存在 3072 维向量；自托管 Qdrant 无此限制。

**推荐**：`embedding_dims` 进 profile，模型按目标选择——自托管保留 3072，Cloudflare 降到 ≤1536 并在能力表标注检索精度差异。

**阻塞**：S1（字段）、M2（CF 侧模型选型）。
**改主意的代价**：**高**（向量一旦入库，改维度要全量重算）。所以这条要在**写入任何生产数据之前**定。

## 第 2 组 · 阻塞 S4/M1/M2，可在 S1 之后再签

### D3 · Web 运行时

**问题**：`web/app` 用什么运行时？

**事实**：shim 分支把它从 Next.js 迁到了 **Moonshine on Bun**（删了 `next.config.js` 等，新增 138 个路由文件）；CF 分支保留 Next.js 源、用 **vinext** 构建到 Workers（纯加法）。二者互斥。

**推荐**：**上游 Next.js 源唯一、与上游同步**；自托管用上游 `web/app/Dockerfile`（Node standalone）；Cloudflare 用 vinext；**不引入 Bun**，Moonshine 打 tag 归档不合入。

**理由**：`web/app` 是上游活跃目录，换框架等于每次上游改动都冲突——正是我们花整个同步在消除的那类问题。

**阻塞**：S4、M1。
**改主意的代价**：**中**（Moonshine 归档 tag 保留，想回去可取；但越晚越贵，因为上游 `web/app` 一直在动）。

**若动机是自托管资源占用**：先量测再说；必要时把非 SSR 页面静态化，或把 Web 放独立小机——不值得为此换运行时。

### D4 · Cloudflare 未迁移路由

**问题**：Cloudflare 目标尚未承载的路由怎么办？（`api-core` 的 `ARCHITECTURE.md` 明确列了 5 类未移植能力）

**选项**

| 方案 | 后果 |
|---|---|
| **A（推荐）支持 `ORIGIN_BACKEND_URL`**：Edge 把未迁移路由回源到**同品牌的自托管后端**（混合部署） | 长尾路由自动由同一份 `backend/` 服务；只有单仓库单契约才可能 |
| B 纯 Cloudflare：未配置时返回上游同形 404，客户端按静态能力表隐藏入口 | 简单；但那 5 类能力在 CF 目标上就是缺的 |

**推荐 A 作为可选项、B 作为默认**：默认 B（不配 `ORIGIN_BACKEND_URL` 就是纯 CF），需要完整能力时配上 A。
**注意**：混合部署下有状态业务路由必须整体在一侧（D1 或 PG），不能跨。

**阻塞**：M2。
**改主意的代价**：**低**（一个配置项）。

### D13 · 目标市场是否含中国大陆 ⏰ 前置期长

**问题**：首发市场？

**若含中国大陆，连带确定四件事**：

1. **主体必须是境内实体**，域名境内备案（ICP + APP 备案；未备案不得分发）
2. **生成式 AI 备案/登记**：调用已备案模型（阿里百炼 Qwen、火山方舟、DeepSeek）走登记成本最低；自托管开源模型需自行备案
3. **服务器落地境内**——与已有的自托管路线天然一致
4. **IAP 策略**：中国区无外链豁免，App 内数字订阅走 WebView 收款有 3.1.1 被拒风险

**阻塞**：D12（主体）、模型供应商选型、S5 的 provider 默认值、B 系列的隐私政策与合规文案。
**改主意的代价**：**高**（主体、备案、服务器位置都要重来）。

### D6 · 蓝牙身份是否与上游分离

**问题**：固件沿用上游的 128 位服务 UUID，还是铸造新基址？

**事实**：换 MCUboot 签名密钥是**必须的**（上游把私钥提交进了仓库），而换密钥后已不可能接受上游 OTA 镜像。

**推荐分离**（新 UUID 基址 + 新密钥）。理由：若沿用上游 UUID，上游 App 会照常连上你的用户设备并把音频送到上游后端，你的设备也会出现在上游的支持队列里。既然换密钥已经打断 OTA 互通，UUID 一并分离几乎不增加成本（每个 SDK 一个常量 × 10 处镜像表）。

**阻塞**：B7。
**改主意的代价**：**高**（设备出货后改 UUID = 存量设备无法被新 App 发现）。
